# 스킬 테스트 케이스

스킬이 **이 스킬의 문서만으로** 좋은 explainer 를 만드는지 본다. 만드는 쪽과 평가하는 쪽은 이 스킬을 만든 대화를 모르는 새 에이전트여야 한다(아는 사람은 문서의 빈틈을 기억으로 메운다).

## 진행

1. **만드는 에이전트** — 아래 요청문만 받는다. `<스킬>/SKILL.md` 를 읽고 그대로 따른다. 끝나면 **막힌 곳·문서가 모호했던 곳·템플릿에서 지우거나 고친 부분**을 목록으로 남긴다.
2. **평가하는 에이전트** — 결과 파일과 `references/rubric.md` 만 받는다. A → B → C 를 적용하고 보고 형식대로 `evals/results/<날짜>-<케이스>.md` 에 쓴다. 같은 방식으로 `references/examples/container-orchestration.html` 도 채점해 기준점과 비교한다.
3. 두 보고를 합쳐 SKILL.md·references·template 에 고칠 것을 정한다.

## 케이스

유형 표(SKILL.md 1절)의 다섯 유형 중 기존 예시가 덮지 않는 것부터 고른다. 예시는 런타임·요청 수명주기에 가깝다.

### bundler — 번들러가 import 그래프를 파일 하나로 합치기 (파이프라인 / 변환)

- 출력 경로: 작업 중인 프로젝트 안 `explainers/bundler/index.html`
- 요청문:
  > `main.ts` 가 `utils.ts` 와 `config.ts` 를 import 하는 작은 프로젝트가 있을 때, 번들러가 이 세 파일을 어떻게 읽어서 하나의 `bundle.js` 로 만드는지(진입점에서 import 따라가기 → 각 파일을 모듈로 감싸기 → 하나로 잇기 → 안 쓰는 export 지우기)를 눈으로 따라가며 이해하는 explainer 를 만들어줘.
- 보고 싶은 것:
  - 축이 **데이터의 모양**(파일 세 개 → 모듈 객체 → 파일 하나)인가. 단계마다 before/after 산출물이 눈에 띄게 다른가 — 거의 안 바뀌는 단계가 있으면 병합했는가
  - 산출물의 코드가 **실제로 돌아갈 법한 번들 형태**(모듈 래퍼 함수, 모듈 맵, require 흉내)인가, 일반론 의사코드인가
  - 다이어그램 라벨이 `main.ts` 가 아니라 **역할**("시작 파일", "도우미 함수들")이고, 변수명을 뜻이 보이게 바꿨다면 푸터에 "실제 이름은 다르다"가 있는가
  - 트리 셰이킹 단계에 **조작**(안 쓰는 export 를 쓰게 바꾸기 → 번들에 다시 들어옴)이 있는가, 결과 문장이 따라붙는가
  - 개수 표시(`파일 3개 → 1개`, 크기)가 스테이지 사이에 있는가
  - 템플릿을 썼는가 — 썼다면 좌표계·`REGBOX` 를 주제에 맞게 바꿨고 B4 라벨 12px 를 지키는가

### hashtable — 해시 테이블의 충돌과 리사이즈 (알고리즘 / 자료구조)

- 출력 경로: `explainers/hashtable/index.html`
- 요청문:
  > 해시 테이블에 키를 넣을 때 버킷이 어떻게 정해지고, 두 키가 같은 버킷에 떨어지면(충돌) 어떻게 되고, 가득 차면(리사이즈) 모든 키가 왜 다시 배치되는지를 단계별로 보여주는 explainer 를 만들어줘. 체이닝 방식 기준으로.
- 보고 싶은 것:
  - 축이 **버킷 배열의 내용물**인가. 중간 상태(충돌 직후, 리사이즈 중)가 본론으로 보이는가 — 최종 결과만 애니메이션하지 않았는가
  - 의사코드가 옆에 있고 **현재 실행 줄이 하이라이트**되는가
  - 불변식("load factor ≤ 0.75")이 한 줄로 명시되는가
  - 리사이즈 단계에 **직접 이동**(키가 옛 버킷에서 새 버킷으로 실제로 움직임)이 있는가, 아니면 색만 바뀌는가 — "무엇이 어디로 갔다"는 움직여야 한다
  - 조작: 키를 하나 더 넣어 충돌을 직접 일으키거나 load factor 슬라이더로 리사이즈 시점을 바꾸는 것 중 하나가 있고, 되돌릴 수 있는가
  - 해시 값·인덱스 숫자가 **실제로 계산된 값**인가(예: `hash("apple") % 8 = 3` 이 일관되게 맞는가)
