# 유형별 시각 문법

축(spine)이 정해지면 그리는 방식이 정해진다. 아무 그림이나 그리지 말고 아래에서 고른다.

## 1. 파이프라인 / 변환
> 번들링, 컴파일, 렌더링, 이미지 처리, ETL

**축:** 데이터의 **모양**이 단계마다 바뀐다.

- 다이어그램: 좌→우 스테이지 박스. 현재 스테이지만 채워진 색, 지나온 건 테두리만, 앞은 흐리게.
- 산출물: **before / after 나란히.** 이게 이 유형의 전부다 — 바뀐 줄만 하이라이트하고 나머지는 그대로 둬서 "뭐가 바뀌었는지"가 눈에 튀게.
- 개수 표시가 강력하다: `파일 3개 → 파일 1개`, `2.1MB → 340KB`. 스테이지 사이에 칩으로.
- 흔한 실패: 스테이지를 너무 잘게 쪼개서 산출물이 거의 안 바뀌는 단계가 생김. **"before/after가 눈에 띄게 다른가"**로 단계를 병합/분할한다.

## 2. 프로토콜 / 합의 / 핸드셰이크
> Raft, Paxos, TCP, TLS, OAuth, 결제 승인 플로우

**축:** 노드별 **상태** + 그 사이 **메시지**.

- 다이어그램: 노드를 원/박스로 배치(고정 위치). 상태는 **색 + 텍스트 라벨 둘 다**로 (색만 쓰면 구분 못 함). 메시지는 노드 사이를 이동하는 점 또는 화살표.
- 타이머·타임아웃이 있으면 노드에 진행 링을 붙인다 — 프로토콜의 절반은 타이밍이다.
- **분기 시나리오 필수:** 정상 경로 → 그다음 실패(노드 다운, 네트워크 분단, 동표). 실패 시나리오가 없으면 왜 이 프로토콜이 이렇게 복잡한지 절대 안 전달된다.
- 각 노드 옆에 그 노드가 아는 것(term, log, 상태)을 작은 표로 붙이면 "합의가 아직 안 됐다"가 보인다.
- 흔한 실패: 메시지만 날아다니고 노드 내부 상태를 안 보여줌. **메시지는 원인, 상태 변화가 결과다.** 결과를 보여줘야 한다.

## 3. 알고리즘 / 자료구조
> 정렬, 탐색, 트리 회전, 해시 충돌, GC

**축:** 컬렉션·포인터·메모리.

- 다이어그램: 배열은 셀 나열, 트리·그래프는 노드. **비교 중인 원소 / 확정된 구간 / 아직 안 본 구간**을 서로 다른 처리로.
- 포인터(i, j, pivot)는 셀 아래 삼각형 마커로 — 이름표를 꼭 붙인다.
- 코드와 동기화: 의사코드를 옆에 두고 **현재 실행 줄을 하이라이트.** 이게 Python Tutor가 잘한 것.
- 불변식(invariant)을 한 줄로 명시하면 밀도가 확 올라간다 — "왼쪽 구간은 항상 정렬됨".
- 흔한 실패: 최종 결과만 애니메이션. **중간 상태가 본론**이다.

## 4. 실행 / 런타임
> 이벤트 루프, 콜스택, async/await, 스케줄러, 렌더 큐

**축:** 스택 · 큐 · 힙의 내용물.

- 다이어그램: 영역 3~4개를 고정 배치(Call Stack / Task Queue / Microtask Queue / Web API). 항목이 push·pop되는 것을 보여준다.
- **push/pop 순간을 강조**한다. 위치 이동보다 "지금 이게 여기서 저기로 갔다"가 핵심.
- 코드 옆에 두고 현재 줄 하이라이트 필수 — 코드 순서와 실행 순서가 다르다는 게 이 유형의 요점이다.
- 흔한 실패: 큐가 비는 시점을 안 보여줌. "마이크로태스크가 다 빌 때까지"가 규칙인데 그 순간이 안 보이면 규칙이 안 남는다.

## 5. 요청 수명주기 / 레이어 통과
> HTTP 요청, 미들웨어 체인, 인터셉터, 캐시 계층

**축:** 요청이 통과하는 **레이어**와 각 레이어가 붙이거나 떼는 것.

- 다이어그램: 수직 레이어 스택. 요청이 내려갔다가 응답이 올라오는 왕복을 보여준다(양파 모델).
- 각 레이어에서 **헤더가 추가되거나 값이 바뀌는 것**을 산출물 패널에 누적 표시.
- 조기 반환(캐시 히트, 인증 실패)을 분기로 넣는다 — 레이어 설명의 핵심은 "어디서 끊기나".

# 인터랙티브 시연 레퍼토리

단계 안에 심을 조작을 여기서 고른다. **주제가 무엇이든 아래 중 하나는 거의 항상 붙는다.**

| 조작 | 언제 쓰나 | 예 |
|---|---|---|
| **대조 토글** | "이 구조가 있을 때 / 없을 때"가 요점일 때 | 두 칼럼을 나란히 두고 버튼 하나로 **양쪽에 같은 사건**을 건다 — 터미널 창 닫기 → 왼쪽은 프로세스 사망, 오른쪽은 살아남음 |
| **실패 주입** | 왜 이렇게 복잡한지가 실패 상황에서만 드러날 때 | `노드 죽이기`, `네트워크 끊기`, `응답 지연 3초`, `캐시 비우기` |
| **파라미터 슬라이더** | 값을 바꿔봐야 패턴이 보일 때 | 노드 수, 타임아웃, 청크 크기. 조작 옆에 "이걸 올리면 무엇이 어떻게 되는지 봐라" 한 줄 필수 |
| **직접 입력** | 입력 모양에 따라 결과가 갈릴 때 | import 문을 고쳐 쓰면 번들 결과가 바뀜. 입력은 **미리 채워두고** 고치게 한다 — 빈 칸은 아무도 안 채운다 |
| **클릭해서 들여다보기** | 내부 상태가 커서 다 못 띄울 때 | 노드를 누르면 그 노드가 아는 것(term/log/헤더)이 옆에 펼쳐짐 |
| **타임라인 스크럽** | 시간 순서 자체가 요점일 때 | 이벤트 루프·경합 상황을 앞뒤로 문질러 보게. 자동 재생과 같이 둔다 |
| **순서 바꾸기** | 순서가 결과를 바꾼다는 게 요점일 때 | 미들웨어를 드래그로 재배치 → 응답 헤더가 달라짐 |
| **직접 이동** | 무엇이 **어디로 갔는지**가 요점일 때 | 꺼낸 항목이 나가는 방향, 뒤의 것들이 한 칸씩 당겨지는 것 |
| **살아 있는 화면** | **계속 일어나는 중**이라는 게 요점일 때 | 로그가 한 줄씩 쌓이고 커서가 깜빡이는 터미널, 떠오르는 알림 |

## 대조 토글 만들기 (가장 자주 쓰는 형태)

한 화면에 **같은 사건, 다른 구조** 둘. 버튼은 하나, 상태는 하나, 렌더는 양쪽 동시에.

```js
let closed = false;                     // 상태는 하나
btn.onclick = () => { closed = !closed; render(); };

function render(){
  btn.textContent = closed ? '터미널 창 다시 열기' : '터미널 창 닫기';
  // 같은 사건이 두 구조에 서로 다르게 적용된다
  setState(plainProcess,  closed ? 'error' : 'done');   // 같이 죽음
  setState(muxProcess,    'done');                      // 살아남음
  verdict.textContent = closed
    ? '왼쪽 프로세스는 창과 함께 종료됐고, 오른쪽은 서버가 쥐고 있어 계속 실행 중입니다.'
    : '양쪽 모두 실행 중입니다. 버튼을 눌러 창을 닫아보세요.';
}
```

- 두 칼럼은 **같은 행 구조**로 맞춘다. 행이 어긋나면 비교가 안 된다 — 한쪽에 없는 레이어는 지우지 말고 "없음" 플레이스홀더로 자리를 남긴다.
- 차이를 만드는 **한 칸만** 강조색. 나머지는 중립색으로 눌러둔다.
- 조작 후 판정 문장(`verdict`)을 하단 고정 위치에 둔다. 매번 같은 자리에서 갱신되어야 눈이 찾는다.
- 버튼 라벨은 토글 상태를 반영해 바뀐다 — `닫기` ↔ `다시 열기`. 안 바뀌면 되돌릴 수 있다는 걸 모른다.

## 움직여야 하는 것 · 토글로 충분한 것

기본은 클래스 토글이다. 아래 셋만 실제로 움직인다 — **그 움직임을 빼고 최종 화면만 봐도 같은 걸 알 수 있다면 움직이지 않는다.**

1. **들어오고 나가기** — 방향이 곧 내용일 때(스택은 넣은 쪽으로, 큐는 반대쪽으로).
2. **밀려남·당겨짐** — 하나를 빼면 나머지가 따라 움직이는 것. 이게 곧 비용이다(배열 앞에서 빼기 = O(n)).
3. **계속 도착함** — 새 것이 쌓이는 동안 오래된 것이 어떻게 되는지.

SVG에서는 `transform` 속성을 그대로 두고 **인라인 CSS transform으로 덮어쓴다.** 제자리 좌표를 JS에 들고 있다가 거기서 밀어낸다:

```js
var BASE = { n_q1:[380,190], /* … 칸마다 제자리 */ };
function setPos(id, dy, opacity, trans){
  var el = document.getElementById(id), b = BASE[id];
  el.style.transition = trans || "none";               // reduced-motion 이면 "none"
  el.style.transform  = "translate("+b[0]+"px,"+(b[1]+dy)+"px)";
  if (opacity !== undefined) el.style.opacity = opacity;
}
```

- **속성(`transform="translate(...)"`)과 인라인 스타일을 섞지 말 것.** CSS transform이 속성을 통째로 덮으므로 x도 항상 같이 써야 한다. x를 빼먹으면 요소가 왼쪽 끝으로 튄다.
- **나가는 것은 움직인 다음에 사라진다.** 처음부터 같이 흐려지면 "나갔다"가 아니라 "없어졌다"로 보인다. 페이드에 지연을 준다 — `transform .7s, opacity .28s linear 420ms`.
- **나가는 길을 화면 안에 비워 둔다.** 제목·라벨이 그 길에 있으면 나가는 칸이 글자를 뚫고 지나간다. viewBox에 여백을 주고 라벨을 레인 밖으로 옮긴다.
- 단계를 옮기면 **밀어낸 것을 전부 제자리로** 되돌린다. 안 그러면 다음 단계가 어긋난 채로 그려진다.
- **들어오는 것과 나가는 것은 이징이 다르다.** 들어오는 건 살짝 지나쳤다 자리잡고(`cubic-bezier(.2,.85,.3,1.08)`), 나가는 건 천천히 떨어졌다 가속해 사라진다. 같은 이징을 쓰면 둘 다 "그냥 바뀌었다"로 보인다.
- **드나드는 화살표는 계속 흐르게 둔다.** 멈춘 화살표는 "이쪽으로 간다"를 말해주지 않는다. active 엣지에 `stroke-dasharray` + `stroke-dashoffset` 애니메이션을 주면 조작하지 않는 동안에도 방향이 읽힌다. 화살표가 20px 남짓이면 흐름이 한 칸도 안 보이므로 40px 이상으로 뽑는다. **단, 점선은 `pending`(대기·전송 중)과 겹치므로 한 페이지에서 둘 다 쓰지 않는다.**
- **이름표를 옮길지, 내용물을 옮길지**를 구분한다. 큐가 한 칸 나아가는 건 보통 **표시(front)가 옮겨가는 것**이고, 배열로 만든 큐에서만 **내용물이 당겨진다.** 둘을 같은 움직임으로 그리면 O(1)과 O(n)의 차이가 지워진다.

## 타이밍 기본값

감을 잡는 출발점이지 규격이 아니다. 매번 새로 정하느라 시간 쓰지 말고 여기서 시작해, 내용이 요구할 때 바꾼다.

| 무엇 | 지속 | 이징 / 비고 |
|---|---|---|
| 자리 옮기기 | **.55s** | `cubic-bezier(.25,.8,.3,1)` — 빨리 떠나 부드럽게 멈춤 |
| 들어오기 | **.5s** | `cubic-bezier(.2,.85,.3,1.08)` — 살짝 지나쳤다 자리잡기 |
| 나가기 | **.7s** | `cubic-bezier(.4,0,.75,.3)` + **페이드는 420ms 뒤에 .28s** |
| 여러 개 순차 | **120~170ms** 간격 | 도착 순서를 보여줄 때. 8개 넘으면 간격을 줄인다 |
| 반복 루프 1주기 | **1.9s** | 로그가 같이 흐르면 로그는 그 절반(950ms) |
| 도착 시 자동 재생 | **0.7s 뒤** | 단계가 그려지고 눈이 자리잡을 시간 |
| 자동 왕복 체류 | 켠 쪽 **2.6s** · 되돌린 쪽 **1.4s** | 결과를 읽을 시간은 길게, 되돌아간 상태는 짧게. 사람이 누르면 루프 종료 |

- **한 단계에 동시에 움직이는 이야기는 하나.** 두 군데가 동시에 움직이면 어디를 봐야 할지 알 수 없다. 대조 시연에서 양쪽이 같이 움직이는 건 예외 — 그건 같은 이야기의 두 결과다.
- **다이어그램을 그리기 전에 나가는 길(레인)부터 잡는다.** 칸 배치를 먼저 하고 나중에 움직임을 붙이면, 나가는 칸이 제목·라벨을 뚫고 지나간다. viewBox 여백 → 레인 → 라벨 순으로 정한다.

## 살아 있는 화면 (흐르는 로그 · 깜빡이는 커서)

"계속 요청이 들어오는 동안"은 정지 화면으로 전달되지 않는다. 이럴 때만 화면을 살려 둔다.

- **타이핑 흉내는 내지 않는다.** 글자를 한 자씩 찍는 건 느리고 읽기 힘들다. **줄 단위로 append**하고, 오래된 줄은 잘라내 길이를 고정한다.
- **커서 하나면 "살아 있다"가 전달된다.** 폭 0.5em 블록에 1초 주기 `steps(1)` 깜빡임.
- **주변이 흐르는 동안 변하지 않는 줄**을 같은 화면에 남긴다 — 그게 보여주려는 것이다(굶은 요청의 대기 시간만 계속 커지는 식).
- **흐르는 화면에는 움직이는 그림을 붙인다.** 로그만 흐르고 다이어그램이 멈춰 있으면 둘이 다른 이야기처럼 보인다. 같은 사건(새 요청 도착)이 양쪽에서 같이 일어나야 한다.
- **반드시 멈춘다.** 타이머를 한 곳에 등록해 두고, 토글을 되돌리거나 단계를 옮길 때 전부 정리한다. 지연 실행(`setTimeout`)도 같이 등록하지 않으면 단계를 옮긴 뒤에 혼자 튀어나온다.

```js
var demoTimers = [];
function demoTick (fn, ms){ var id = setInterval(fn, ms); demoTimers.push(id); return id; }
function demoDelay(fn, ms){ var id = setTimeout (fn, ms); demoTimers.push(id); return id; }
function demoStop(){                                        // 단계 전환·토글마다
  demoTimers.forEach(function(id){ clearInterval(id); clearTimeout(id); });
  demoTimers = [];
}
```

## 시연의 흔한 실패

- **눌러도 별로 안 변한다.** 조작의 값어치는 변화량으로 정해진다. 변화가 미미하면 그 조작은 빼거나, 더 센 사건으로 바꾼다.
- **한 화면에 조작이 셋.** 무엇을 눌러야 할지 고민하는 순간 이해가 아니라 UI 탐색이 시작된다.
- **되돌릴 수 없다.** 새로고침해야 원상복구되면 비교를 한 번밖에 못 한다.
- **결과 해석이 없다.** 뭐가 바뀌었는지 봤어도 "그래서 그게 왜 중요한지"는 문장으로 말해줘야 남는다.

# 상태 표현 규칙 (공통)

**클래스 토글로 상태를 표현한다.** DOM을 다시 그리지 말고 같은 요소의 클래스만 바꾼다. 그래야 CSS transition이 붙어 "변했다"가 지각되고, 독자가 같은 시스템을 계속 보고 있다고 느낀다.

```js
el.classList.remove('idle','active','done','error');
el.classList.add(state);
```

상태는 **최대 4~5종**. 더 늘면 색을 못 외운다. 색만으로 구분하지 말고 **테두리 모양·라벨·아이콘 중 하나를 같이** 쓴다(색각 이상 + 흑백 출력 대응).

전형적인 세트:
| 상태 | 의미 | 처리 |
|---|---|---|
| `idle` | 아직 안 닿음 | 흐린 테두리, 채움 없음 |
| `active` | 지금 처리 중 | 강조색 테두리 + 은은한 펄스 |
| `done` | 처리 완료 | 채워진 배경 |
| `pending` | 대기·전송 중 | 점선 테두리 |
| `error` | 실패 경로 | 경고색 (강조색과 다른 계열) |

**`prefers-reduced-motion`일 때 애니메이션은 끄되 최종 상태는 즉시 반영한다.** 애니메이션이 정보를 나르는 유일한 수단이면 안 된다 — 정지 화면만 봐도 상태를 읽을 수 있어야 한다.

# 산출물 패널 (②) 만들기

- **before/after는 나란히**(넓은 화면) → **위아래**(좁은 화면). `grid-template-columns` 미디어 쿼리.
- 바뀐 줄만 배경 하이라이트 + 좌측 컬러 바. 전체를 칠하면 아무것도 안 보인다.
- 코드는 `<pre><code>`에 직접 하이라이트 `<span>`을 심는다. 하이라이터 라이브러리를 부르지 않는다(CSP·의존성).
- 로그를 보여줄 땐 **실제 로그 포맷**을 흉내낸다 — 타임스탬프, 레벨, 화살표. 가짜 티가 나면 신뢰가 깨진다.
- 숫자가 열로 정렬되면 `font-variant-numeric: tabular-nums`.

# 흔한 실패 (레퍼런스에서 확인된 것)

1. **그냥 스킵한다.** 독자는 인터랙션을 안 누르고 스크롤로 지나간다.
   → 대책: 다음 단계로 넘어가는 것을 **버튼으로만** 열어두고(스텝 방식), 한 화면에 한 단계만 둔다. 길게 스크롤되는 문서로 만들지 않는다.
2. **위젯만 있고 안내가 없다.** 슬라이더를 줬는데 뭘 봐야 하는지 안 알려줌.
   → 대책: 조작 요소마다 "이걸 움직이면 X가 어떻게 되는지 봐라" 한 줄.
3. **선행 지식을 가정한다.** 3단계에서 갑자기 모르는 용어가 나옴.
   → 대책: 1단계에서 등장 요소와 용어를 **범례로 먼저 고정**하고, 이후 단계는 그 어휘만 쓴다.
4. **게이미피케이션으로 도망간다.** 점수·뱃지를 붙여도 이해는 안 는다.
   → 목표는 행동 변화가 아니라 **지식 변화**.
5. **일반론 예시.** `foo`, `bar`, `Component A`.
   → 실제 이름, 실제 값, 실제 파일 경로를 쓴다.
