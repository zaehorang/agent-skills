# 유형별 시각 문법

축(spine)이 정해지면 그리는 방식이 정해진다. 아무 그림이나 그리지 말고 아래에서 고른다.

## 1. 파이프라인 / 변환
> 번들링, 컴파일, 렌더링, 이미지 처리, ETL

**축:** 데이터의 **모양**이 단계마다 바뀐다.

- 다이어그램: 좌→우 스테이지 박스. 현재 스테이지만 채워진 색, 지나온 건 테두리만, 앞은 흐리게.
- 산출물: **before / after 나란히.** 이게 이 유형의 전부다 — 바뀐 줄만 하이라이트하고 나머지는 그대로 둬서 "뭐가 바뀌었는지"가 눈에 튀게.
- 개수 표시가 강력하다: `파일 3개 → 파일 1개`, `2.1MB → 340KB`. 스테이지 사이에 칩으로.
- 흔한 실패: 스테이지를 너무 잘게 쪼개서 산출물이 거의 안 바뀌는 단계가 생김. **"before/after가 눈에 띄게 다른가"**로 단계를 병합/분할한다.

## 2. 프로토콜 / 합의 / 핸드셰이크
> Raft, Paxos, TCP, TLS, OAuth, 결제 승인 플로우

**축:** 노드별 **상태** + 그 사이 **메시지**.

- 다이어그램: 노드를 원/박스로 배치(고정 위치). 상태는 **색 + 텍스트 라벨 둘 다**로 (색만 쓰면 구분 못 함). 메시지는 노드 사이를 이동하는 점 또는 화살표.
- 타이머·타임아웃이 있으면 노드에 진행 링을 붙인다 — 프로토콜의 절반은 타이밍이다.
- **분기 시나리오 필수:** 정상 경로 → 그다음 실패(노드 다운, 네트워크 분단, 동표). 실패 시나리오가 없으면 왜 이 프로토콜이 이렇게 복잡한지 절대 안 전달된다.
- 각 노드 옆에 그 노드가 아는 것(term, log, 상태)을 작은 표로 붙이면 "합의가 아직 안 됐다"가 보인다.
- 흔한 실패: 메시지만 날아다니고 노드 내부 상태를 안 보여줌. **메시지는 원인, 상태 변화가 결과다.** 결과를 보여줘야 한다.

## 3. 알고리즘 / 자료구조
> 정렬, 탐색, 트리 회전, 해시 충돌, GC

**축:** 컬렉션·포인터·메모리.

- 다이어그램: 배열은 셀 나열, 트리·그래프는 노드. **비교 중인 원소 / 확정된 구간 / 아직 안 본 구간**을 서로 다른 처리로.
- 포인터(i, j, pivot)는 셀 아래 삼각형 마커로 — 이름표를 꼭 붙인다.
- 코드와 동기화: 의사코드를 옆에 두고 **현재 실행 줄을 하이라이트.** 이게 Python Tutor가 잘한 것.
- 불변식(invariant)을 한 줄로 명시하면 밀도가 확 올라간다 — "왼쪽 구간은 항상 정렬됨".
- 흔한 실패: 최종 결과만 애니메이션. **중간 상태가 본론**이다.

## 4. 실행 / 런타임
> 이벤트 루프, 콜스택, async/await, 스케줄러, 렌더 큐

**축:** 스택 · 큐 · 힙의 내용물.

- 다이어그램: 영역 3~4개를 고정 배치(Call Stack / Task Queue / Microtask Queue / Web API). 항목이 push·pop되는 것을 보여준다.
- **push/pop 순간을 강조**한다. 위치 이동보다 "지금 이게 여기서 저기로 갔다"가 핵심.
- 코드 옆에 두고 현재 줄 하이라이트 필수 — 코드 순서와 실행 순서가 다르다는 게 이 유형의 요점이다.
- 흔한 실패: 큐가 비는 시점을 안 보여줌. "마이크로태스크가 다 빌 때까지"가 규칙인데 그 순간이 안 보이면 규칙이 안 남는다.

## 5. 요청 수명주기 / 레이어 통과
> HTTP 요청, 미들웨어 체인, 인터셉터, 캐시 계층

**축:** 요청이 통과하는 **레이어**와 각 레이어가 붙이거나 떼는 것.

- 다이어그램: 수직 레이어 스택. 요청이 내려갔다가 응답이 올라오는 왕복을 보여준다(양파 모델).
- 각 레이어에서 **헤더가 추가되거나 값이 바뀌는 것**을 산출물 패널에 누적 표시.
- 조기 반환(캐시 히트, 인증 실패)을 분기로 넣는다 — 레이어 설명의 핵심은 "어디서 끊기나".

# 상태 표현 규칙 (공통)

**클래스 토글로 상태를 표현한다.** DOM을 다시 그리지 말고 같은 요소의 클래스만 바꾼다. 그래야 CSS transition이 붙어 "변했다"가 지각되고, 독자가 같은 시스템을 계속 보고 있다고 느낀다.

```js
el.classList.remove('idle','active','done','error');
el.classList.add(state);
```

상태는 **최대 4~5종**. 더 늘면 색을 못 외운다. 색만으로 구분하지 말고 **테두리 모양·라벨·아이콘 중 하나를 같이** 쓴다(색각 이상 + 흑백 출력 대응).

전형적인 세트:
| 상태 | 의미 | 처리 |
|---|---|---|
| `idle` | 아직 안 닿음 | 흐린 테두리, 채움 없음 |
| `active` | 지금 처리 중 | 강조색 테두리 + 은은한 펄스 |
| `done` | 처리 완료 | 채워진 배경 |
| `pending` | 대기·전송 중 | 점선 테두리 |
| `error` | 실패 경로 | 경고색 (강조색과 다른 계열) |

**`prefers-reduced-motion`일 때 애니메이션은 끄되 최종 상태는 즉시 반영한다.** 애니메이션이 정보를 나르는 유일한 수단이면 안 된다 — 정지 화면만 봐도 상태를 읽을 수 있어야 한다.

# 산출물 패널 (②) 만들기

- **before/after는 나란히**(넓은 화면) → **위아래**(좁은 화면). `grid-template-columns` 미디어 쿼리.
- 바뀐 줄만 배경 하이라이트 + 좌측 컬러 바. 전체를 칠하면 아무것도 안 보인다.
- 코드는 `<pre><code>`에 직접 하이라이트 `<span>`을 심는다. 하이라이터 라이브러리를 부르지 않는다(CSP·의존성).
- 로그를 보여줄 땐 **실제 로그 포맷**을 흉내낸다 — 타임스탬프, 레벨, 화살표. 가짜 티가 나면 신뢰가 깨진다.
- 숫자가 열로 정렬되면 `font-variant-numeric: tabular-nums`.

# 흔한 실패 (레퍼런스에서 확인된 것)

1. **그냥 스킵한다.** 독자는 인터랙션을 안 누르고 스크롤로 지나간다.
   → 대책: 다음 단계로 넘어가는 것을 **버튼으로만** 열어두고(스텝 방식), 한 화면에 한 단계만 둔다. 길게 스크롤되는 문서로 만들지 않는다.
2. **위젯만 있고 안내가 없다.** 슬라이더를 줬는데 뭘 봐야 하는지 안 알려줌.
   → 대책: 조작 요소마다 "이걸 움직이면 X가 어떻게 되는지 봐라" 한 줄.
3. **선행 지식을 가정한다.** 3단계에서 갑자기 모르는 용어가 나옴.
   → 대책: 1단계에서 등장 요소와 용어를 **범례로 먼저 고정**하고, 이후 단계는 그 어휘만 쓴다.
4. **게이미피케이션으로 도망간다.** 점수·뱃지를 붙여도 이해는 안 는다.
   → 목표는 행동 변화가 아니라 **지식 변화**.
5. **일반론 예시.** `foo`, `bar`, `Component A`.
   → 실제 이름, 실제 값, 실제 파일 경로를 쓴다.
