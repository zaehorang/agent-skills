# mechanism-explainer

**"이게 내부적으로 어떻게 돌아가는가"를 순차적으로 따라가며 이해하는 단일 HTML 파일**을 만든다.

글로 읽으면 안 잡히는 것 — 상태가 단계마다 어떻게 바뀌는지, 어떤 데이터가 어떤 모양으로 변형되는지, 왜 이 순서여야 하는지 — 를 **눈으로 확인**하게 만드는 것이 목적이다.

## 이건 이런 게 아니다

| 아님 | 맞음 |
|---|---|
| 개념 요약 문서를 예쁘게 만든 것 | 매 단계 **상태가 실제로 바뀌는** 걸 보여주는 것 |
| 위젯·슬라이더를 늘어놓은 것 | **주의를 특정 현상으로 유도**하는 가이드된 순서 |
| 도식 한 장 | 전/후를 비교할 수 있는 **스텝 시퀀스** |
| 일반론적 예시(foo, bar) | **실제로 돌아가는 코드·로그·페이로드** |
| 아는 사람만 읽히는 이름표 | **역할로 부르고**, 모를 용어는 그 단계 안에서 푼다 |
| 채팅에 띄우는 일회성 미리보기 | 프로젝트 안에 남는 **실제 .html 파일** |

## 고정된 것 · 자유로운 것

**고정 (지키지 않으면 explainer 가 아니라 예쁜 요약 문서가 된다)**
축 하나로 꿴다 · 단계마다 상태·산출물·이유가 같이 보인다 · 이름 대신 역할로 부른다 ·
용어는 그 용어가 나온 단계 안에서 푼다 · 조작에는 결과 문장이 따라붙는다 · 의존성 없는 단일 파일.

**자유 (내용이 정한다)**
단계 수, 레이아웃, 시각 문법, 어떤 조작을 심을지, 움직일지 말지, 수치와 이징.
`references/patterns.md` 의 목록·표·코드는 **고르는 재료이자 출발점**이지 따라야 할 순서가 아니다.
주제가 다른 문법을 요구하면 버리고 새로 짜도 된다. 다만 거기 적힌 **함정**은 이미 값을 치르고 얻은 것이니 읽고 시작한다.

## 진행

### 0. 어디에 만들지 한 줄로 정한다

사용자가 경로를 말했으면 그것. 아니면 프로젝트에 이미 있는 자리(`explainers/`, `docs/`)를 쓰고, 그것도 없으면 `explainers/<주제-슬러그>/index.html`. 슬러그는 영문 케밥에 기술·개념만 (`bundling-pipeline`, `raft-consensus`).

**의존성 0개 · 단일 파일 · 빌드 없이 브라우저에서 바로 열린다.** 외부 CSS·JS·이미지를 부르지 않는다(웹폰트는 예외).

### 1. 축(spine)을 정한다 — 무엇이 단계마다 바뀌는가

이걸 못 정하면 나머지가 다 장식이 된다. 대상이 어느 유형인지 먼저 판별한다:

| 유형 | 축 | 예 |
|---|---|---|
| **파이프라인 / 변환** | 데이터의 모양 | 번들링, 컴파일, 렌더링, ETL |
| **프로토콜 / 합의** | 노드별 상태 + 오가는 메시지 | Raft, TCP 핸드셰이크, OAuth |
| **알고리즘 / 자료구조** | 메모리·포인터·컬렉션 | 정렬, 트리 회전, GC |
| **실행 / 런타임** | 콜스택·큐·힙 | 이벤트 루프, 스케줄러, async |
| **요청 수명주기** | 요청이 통과하는 레이어 | HTTP 요청, 미들웨어 체인 |

축이 정해지면 **단계를 5~9개**로 쪼갠다. 각 단계는 "이 단계가 끝나면 무엇이 이전과 달라져 있나"로 한 줄 답이 나와야 한다. 안 나오면 그건 단계가 아니라 설명이다 — 앞뒤에 합친다. 주제가 작아서 단계가 2~3개밖에 안 나오면 억지로 늘리지 않는다 — 한 화면에 조작 하나로 끝내도 된다(5절).

### 2. 3단 구조로 만든다

각 단계마다 세 가지가 동시에 보여야 한다. **이게 이 스킬의 핵심 패턴이다.**

```
┌─────────────────────────────────────────┐
│ ① 상태 다이어그램  — 지금 어디에 있나       │  단계마다 노드/엣지 색·클래스가 바뀜
│    (단계가 바뀌어도 같은 자리에 고정)        │
├─────────────────────────────────────────┤
│ ② 산출물          — 뭐가 실제로 바뀌었나    │  before/after 코드·로그·페이로드
│                                          │  바뀐 줄은 하이라이트
├─────────────────────────────────────────┤
│ ③ 내레이션        — 왜 이 단계가 필요한가   │  없으면 뭐가 깨지는지까지
└─────────────────────────────────────────┘
```

- **① 다이어그램은 단계마다 새로 그리지 않는다.** 같은 SVG가 계속 있고, **클래스만 갈아끼워** 상태가 변한다. 독자가 "같은 시스템의 다른 시점"으로 읽게 하는 장치.
- **② 산출물은 진짜여야 한다.** 실제로 돌아가는 코드, 실제 로그 포맷, 실제 JSON. 지어낸 일반론은 이해를 못 만든다.
- **③ 내레이션은 "무엇을 한다"가 아니라 "왜 이래야 하나".** 대안이 왜 안 되는지 한 줄이 들어가면 훨씬 오래 남는다.

### 3. 이름이 아니라 역할로 부른다

**독자가 모르는 이름은 아무 정보도 주지 않는다.** `main.tsx`, `AuthMiddleware`, `n_a` 같은 라벨만 있는 다이어그램은 이미 아는 사람만 읽을 수 있다.

- **다이어그램·칩·스텝 라벨은 "그게 하는 일"로 쓴다.** 진짜 이름이 필요하면 **역할을 크게, 이름을 작게** 함께 표시한다.
  - ✗ `config.ts` → ✓ **표 설정값** <sub>config.ts</sub>
  - ✗ `resolution` → ✓ **파일 찾아 나가기**
  - ✗ `n_b`, `mod_2` → 코드 안 식별자도 의미가 드러나게
- **단계 제목(`title`)은 전문용어 없이 한 문장.** 전문용어는 본문(`desc`)에서 처음 쓸 때 한 번 풀고, 그다음부터 쓴다.
- 예시 코드 안의 변수명도 마찬가지 — 생성된 코드를 보여줄 때 `a`, `mod1` 대신 `표설정_모듈`처럼 뜻이 보이게 바꿔도 된다. **정확한 재현보다 이해가 우선**이고, 그럴 땐 푸터에 "실제 구현의 이름은 다르다" 한 줄을 남긴다.

### 4. 모를 수 있는 용어는 **그 용어가 나온 단계 안에** 둔다

본문 흐름을 끊지 않으면서 막힌 사람을 구제하는 장치. **필수다.**

**위치가 핵심이다.** 페이지 최하단에 사전을 몰아두면 아무도 안 본다 — 막힌 사람은 이미 그 자리에서 멈췄고, 끝까지 스크롤해 되돌아올 만큼 동기가 남아 있지 않다. **그 용어를 처음 쓴 단계의 바로 아래**에 둔다.

- 각 단계 정의에 `terms` 목록을 달고, 그 단계 패널 아래에 `<details>` 토글로 렌더한다. 기본은 접힘 — 아는 사람은 지나가고, 막힌 사람만 편다.
- **단계당 2~4개.** 그 단계에서 **처음 등장한** 것만. 앞 단계에서 이미 푼 용어는 다시 넣지 않는다(중복은 "안 읽어도 되는 것"이라는 신호를 준다).
- 각 항목은 **한두 문장**. 정의 + "지금 이 단계에서 왜 나오는가". 사전을 옮겨 적지 않는다.
- 단계에 새 용어가 없으면 `terms`를 비운다. **칸을 채우려고 만들지 않는다.**

```js
terms: [
  { ko:"번들", en:"bundle",
    def:"여러 파일을 <b>하나로 합친 결과물</b>. 브라우저가 파일마다 따로 요청하지 않아도 되게 만든다." }
]
```

### 5. 따라가게 하고, 직접 해보게 한다

**진행은 가이드된 순차 진행이 기본이다** (Secret Lives of Data 방식). 자유 탐색보다 정해진 순서를 따라가게 하는 게 내부 원리 설명엔 낫다.

필수:
- **이전 / 다음** 버튼 + `←` `→` 키보드
- **스텝 레일** — 전체 몇 단계 중 어디인지, 각 단계 라벨이 보이는 상단 네비. 클릭으로 점프 가능
- **현재 / 전체** 카운트

**그리고 가능한 단계마다 조작을 하나 심는다.** 읽고 넘어간 단계와 눌러보고 결과를 본 단계는 남는 게 다르다. "이 단계가 없으면 뭐가 깨지나"를 내레이션으로 쓰는 대신 **독자가 직접 깨뜨려 보게** 만들 수 있으면 그렇게 한다.

시연 하나가 갖춰야 할 것:

- **조작은 한 단계에 하나.** 무엇을 눌러야 하는지 고민하게 만들면 이미 실패다. 버튼 라벨은 일어날 일 그대로 (`터미널 창 닫기`, `노드 2 죽이기`).
- **누르면 즉시, 눈에 띄게 달라진다.** 변화가 칩 하나 색깔뿐이면 조작이 아니라 장식이다.
- **대조가 보인다.** 있을 때 / 없을 때를 나란히 두고 **같은 조작을 양쪽에 동시에** 걸면 차이가 한 번에 읽힌다. 이게 "왜 이 구조가 필요한가"를 가장 싸게 전달하는 방법이다.
- **되돌릴 수 있다.** 원상복구가 있어야 사람이 겁 없이 누르고, 두 번 세 번 비교한다.
- **단계를 넘길 때 화면을 스크롤하지 않는다.** 읽던 자리가 튀면 무엇이 바뀌었는지도 같이 놓친다. 무대가 화면 밖으로 완전히 나갔을 때만 최소한으로 끌어온다.
- **움직임이 그 단계의 요점이면 도착했을 때 저절로 왕복 반복한다.** 한 번만 재생하고 멈추면 그 순간 다른 데를 보던 사람은 영영 못 본다. **사람이 버튼을 누르면 거기서 루프를 멈추고 조작권을 넘긴다** — 내가 만지는데 화면이 혼자 계속 움직이면 조작이 아니라 방해다.
- **결과를 한 줄로 말해준다.** 조작 후 "그래서 무슨 일이 생겼나"를 문장으로 남긴다. 애니메이션만 보여주고 해석을 독자에게 떠넘기지 않는다.

**바뀐 것을 어떻게 보여줄지는 네 가지로 갈린다.**

| 보여줄 것 | 수단 |
|---|---|
| 상태가 달라졌다 | **클래스 토글** — 색·테두리·라벨. 기본값이고, 대부분 이걸로 끝난다 |
| **무엇이 어디로 갔다** | **실제로 움직인다** — 들어오고 나가는 방향, 뒤가 앞으로 당겨지는 것, 순서가 밀리는 것은 색으로 못 보여준다 |
| **계속 일어나는 중이다** | **화면을 살려 둔다** — 로그가 한 줄씩 흐르고, 커서가 깜빡이고, 알림이 떠오른다. 정지 화면은 "계속"을 못 보여준다 |
| **저것만 안 움직인다** | **움직이지 않는다** — 주변이 흐르는 동안 그대로인 것이 보여야 한다. 굶음·교착·누수가 여기 해당한다 |

움직임은 장식이 아니라 그 자체로 정보일 때만 쓴다. 판단 기준 하나: **그 움직임을 빼고 최종 화면만 봤을 때 같은 걸 알 수 있으면, 움직이지 말아야 한다.**

어느 쪽을 쓰든 공통 규칙:
- `prefers-reduced-motion`이면 **최종 상태로 즉시.** 움직임이 정보를 나르는 유일한 수단이면 안 된다.
- 흐르는 화면은 **반드시 멈출 수 있어야** 하고, 단계를 벗어나면 스스로 멈춰야 한다. 안 멈추면 뒤 단계에서 유령처럼 계속 돈다.

무엇을 조작 가능하게 만들지(대조 토글, 실패 주입, 슬라이더, 스크럽 등)는 `references/patterns.md`의 시연 레퍼토리에서 고른다.

**포맷은 고정이 아니다.** 스텝 시퀀스가 기본형이지만, 주제가 "이 둘의 차이"나 "이게 없으면 어떻게 되나" 하나로 끝나면 **한 화면 + 조작 하나**가 더 낫다. 단계 수가 아니라 축(1절)이 보이는지가 기준이다.

선택 (내용이 요구할 때만):
- 자동 재생 / 속도 조절 — 시간에 따른 반복(폴링, 이벤트 루프)이 축일 때
- **분기 시나리오** — best case 먼저, 그 다음 worst case(실패·경합·파티션). 프로토콜류엔 거의 항상 넣는다

### 6. 열어서 눌러본다

- **모든 단계를 한 번씩** 넘겨본다. 브라우저 도구가 없으면 코드로 상태 전이를 따라간다.
- **라벨** — 다이어그램과 스텝 레일에 뜻 없는 이름만 남은 곳이 없는지.
- **용어** — 전문용어가 처음 나온 그 단계에 뜻이 같이 있는지.
- **조작** — 눌러서 실제로 바뀌는지, 되돌아오는지, 결과 문장이 같이 뜨는지.
- **움직임** — 나가는 것이 화면 안에서 보이게 나가는지, 라벨을 뚫지 않는지, 단계를 옮기면 제자리로 돌아오고 흐르는 화면이 멈추는지, `prefers-reduced-motion`에서 최종 상태가 그대로 읽히는지.
- 라이트/다크 양쪽, 좁은 화면에서 body에 가로 스크롤이 안 생기는지(넓은 표·코드는 자기 컨테이너가 `overflow-x: auto`).

애니메이션 **중간** 프레임은 자동으로 잡기 어렵다 — 백그라운드 탭은 `requestAnimationFrame`이 멈춰 트랜지션이 진행되지 않고, 스크린샷은 도구 왕복 때문에 대개 끝난 뒤에 찍힌다. ① 최종 상태는 스크린샷으로 ② 중간 동작은 `element.style` 값을 코드로 읽어서 ③ 모양이 궁금하면 transition 지속을 잠깐 몇 초로 늘려 한 프레임 고정해서 본다.

## 페이지를 짤 때

한 파일에 `<style>` + 마크업 + `<script>`. 구조는 **단계 배열 하나와 그걸 그리는 함수 하나**면 끝난다.

```js
var STEPS = [{
  nav:"번들",                                  // 스텝 레일에 뜨는 2~5자
  title:"이 단계가 끝나면 뭐가 달라져 있나",      // 전문용어 없이 한 문장
  desc:"<p>왜 이 단계가 필요한가</p>",
  graph:{ done:["n_a"], active:["n_b"], idle:["n_c"], edges:{ e_a_b:"active" } },
  panels:"…before/after 코드·로그 HTML…",
  terms:[{ ko:"번들", en:"bundle", def:"…" }],  // 이 단계에서 처음 나온 것만
  enter:fillIn,                                 // (선택) 도착하면 한 번 움직일 것
  demo:{ auto:true, label:"캐시 비우기", labelOn:"되돌리기",
         hint:"무엇을 보라는 한 줄",
         run:function(on){ /* 그래프·위치를 바꾸고 */ return "판정 문장"; } }
}];
```

`go(n)` 하나가 단계를 그린다 — 텍스트 교체 → 이전 단계 움직임 제자리로 → 그래프 클래스 적용 → `enter` → 시연 버튼 렌더. 이전/다음 버튼과 `←` `→` 키가 `go`를 부른다.

**직접 짜면 틀리기 쉬운 여섯 가지** (전부 값을 치르고 얻은 것)

1. **다이어그램은 다시 그리지 않는다.** 같은 SVG의 클래스만 교체한다 — `el.classList.remove.apply(el.classList, STATES); el.classList.add(s)`. 상태는 4~5종까지, 색만으로 구분하지 말고 테두리·라벨을 같이 쓴다.
2. **SVG를 움직일 때 x를 같이 쓴다.** 인라인 `style.transform`이 `transform` 속성을 통째로 덮는다. 제자리 좌표표를 들고 `translate(x, y+dy)`로 **항상 둘 다** 쓴다 — x를 빼먹으면 요소가 왼쪽 끝으로 튄다.
3. **시작 위치 → 강제 리플로우 → 목표 위치.** 사이에 `void document.documentElement.offsetWidth`가 없으면 애니메이션 없이 순간이동한다.
4. **타이머는 한 배열에 등록하고 한 번에 정리한다.** `setInterval`뿐 아니라 `setTimeout`도. 단계 전환·토글마다 비운다.
5. **테마 토큰은 세 군데에 쓴다.** `:root`(라이트) · `@media (prefers-color-scheme:dark){ :root:not([data-theme="light"]) }` · `:root[data-theme="dark"]`. `body` 배경을 토큰으로 명시하지 않으면 뷰어 배경이 비친다.
6. **`go`는 스크롤을 건드리지 않는다.** 무대가 화면 밖으로 완전히 나갔을 때만 최소한으로 끌어온다.

타이밍은 이 값에서 시작한다 — 자리 옮기기 `.55s` · 들어오기 `.5s`(살짝 오버슈트) · 나가기 `.7s`에 **페이드는 420ms 뒤** · 순차 간격 `120~170ms` · 자동 왕복은 켠 쪽 `2.6s` 되돌린 쪽 `1.4s`.

더 필요하면 `references/patterns.md` — 유형별 시각 문법, 시연 레퍼토리, 움직임·살아 있는 화면 만드는 법, 흔한 실패. **통으로 읽지 말고 해당 유형 절과 쓰기로 한 장치 절만 편다.**

## 원칙 (레퍼런스에서)

1. **Do & Show & Tell** — 추상 개념은 글로, 시간에 따른 변화는 애니메이션으로, 프로세스·시스템은 인터랙션으로. 하나로 다 하려 들지 않는다. *(Nicky Case)*
2. **주의를 유도한다** — 인터랙티브 위젯을 늘어놓는 것과 explorable explanation의 차이는, 후자가 **독자가 무엇을 봐야 하는지 의도적으로 안내**한다는 것. *(Bret Victor)*
3. **작게 시작해 쌓는다** — 메커니즘을 하나씩 분리해 보여준 뒤 조합한다. 1단계부터 전체 구조를 던지지 않는다.
4. **최선 다음에 최악** — 정상 경로를 먼저 끝까지 보여주고, 그 다음 실패 경로. 순서가 반대면 둘 다 안 남는다. *(Secret Lives of Data)*
5. **상태를 코드와 동기화한다** — 지금 실행 중인 줄과 그때의 내부 상태가 **같은 화면에** 있어야 한다. *(Python Tutor)*
6. **선행 지식을 가정하지 않는다** — 3단계에서 처음 보는 용어가 튀어나오면 거기서 이해가 멈춘다. 등장 어휘는 1단계 범례에서 고정하고, 나머지는 그 용어가 나온 단계가 받는다. *(Nicky Case의 "prerequisite scaffolding")*
