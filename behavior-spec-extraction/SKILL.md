# Behavior Spec Extraction

구현을 **관측 가능한 동작**으로만 다시 쓴다. 독자는 그 기술을 모르는 개발자·엔지니어·기획자이고, 명세를 읽고 "이게 맞다/틀리다"를 판단할 수 있어야 한다.

핵심 제약 셋:

1. 명세는 **구현이 아니라 관측 가능한 동작**만 기술한다.
2. 해당 기술을 모르는 사람이 읽을 수 있는 **자연어**로 번역한다.
3. **클래스·메서드·타입 이름을 쓰지 않는다.** 사용자 관점 동작으로만 서술해 기술을 몰라도 검수가 가능하게 한다.

## When to use

- 레거시/타 스택 코드를 다른 기술로 옮기기 전에 현재 동작을 확정할 때 (Unity→React, UIKit→SwiftUI, jQuery→모던 프레임워크 등)
- 인수인계·리뷰용으로 모듈이 실제로 무엇을 하는지 비전문가가 읽을 수 있게 남길 때
- 구현은 있는데 요구사항 문서가 없어서, 무엇이 의도된 동작이고 무엇이 사고인지 사람 손으로 확인받아야 할 때
- 코드가 없는 신규 기능 명세라면 같은 템플릿과 규칙을 그대로 쓰되 2단계(관측면 수집)를 사용자 인터뷰로 대체한다

## Workflow

### 1. 기능 경계를 먼저 자른다

**파일 단위로 자르지 않는다.** 명세 하나의 단위는 "사용자 눈에 하나로 보이는 동작"이다.

- 한 클래스가 세 가지 일을 하면 → 명세 세 개
- 다섯 파일이 협력해 한 화면 동작을 만들면 → 명세 하나
- 경계가 애매하면 "이 동작만 사라지면 사용자가 무엇을 못 하게 되는가"로 물어본다. 답이 한 문장이면 하나의 기능이다.

자른 목록을 먼저 사용자에게 보여주고 동의를 받은 뒤 본문을 쓴다. 경계가 틀리면 이후 작업 전부가 틀린다.

### 2. 관측면만 수집한다

코드를 읽되 다음 넷만 뽑아낸다.

- **발동 계기**: 어떤 사용자 행동 / 외부 이벤트 / 시간 조건이 이 동작을 시작시키는가
- **외부에서 받는 값**: 무엇이 들어오고, 누가 그것을 정하는가
- **밖에 남는 변화**: 화면, 저장된 데이터, 서버로 나가는 것, 사용자에게 보이는 메시지
- **실패 경로**: 무엇이 어긋날 수 있고, 그때 사용자가 겪는 일은 무엇인가

내부 자료구조, 호출 순서, 파일 분리 방식, 최적화는 **이 단계에서 버린다.** 밖에서 관측되지 않으면 명세에 존재하지 않는다.

### 3. 번역한다

`references/translation-rules.md`를 읽고 규칙을 적용한다. 기술 무관 규칙 7개와 언어·프레임워크별 예시표가 있다.

### 4. 초안을 쓴다

`references/spec-template.md`의 6섹션 템플릿과 좋은 예/나쁜 예 대조를 따른다. 린터를 통과하는 완성본 하나가 `references/example-spec.md`에 있으니 톤과 밀도의 기준으로 삼는다.

### 5. 린트를 통과시킨다

```bash
python3 ~/.claude/skills/behavior-spec-extraction/scripts/lint_spec.py <spec-path>...
```

stdlib만 쓰고 의존성이 없다. 잡는 것:

- 식별자 누출 (CamelCase, `snake_case`, `점.연결`, `호출()`, 코드 블록)
- 프레임워크·구현 용어 사전 (코루틴, 싱글턴, 리듀서, 폴링, 메서드, 캐시 …)
- 6섹션 누락
- Goal이 한 문장이 아닌 경우
- Acceptance 항목이 검증 조건 없이 쓰였거나, 여러 조건이 한 항목에 뭉친 경우

**에러가 남아 있으면 명세를 사용자에게 제출하지 않는다.** 고쳐서 통과시킨 뒤 제출한다. 경고는 판단해서 고치거나 근거를 남긴다.

관측 가능한데도 린터가 잡는 문자열(사용자에게 실제로 보이는 문구, 사용자가 지정하는 파일 경로 등)은 그 줄 끝에 `<!-- lint-ok -->`를 붙여 통과시킨다. 남발하면 스킬의 목적이 무너지므로, 붙일 때마다 "비전문가가 이 문자열을 화면에서 볼 수 있는가"로 자문한다.

### 6. 모르는 것은 추측하지 않는다

코드만으로는 알 수 없는 것이 반드시 나온다. 왜 3초인지, 이 예외 처리가 의도인지 사고인지, 이 분기가 아직 쓰이는지. 지어내지 말고 명세 끝의 `열린 질문` 섹션에 **질문 형태로** 남기고, 사용자에게 그 목록을 함께 전달한다.

### 7. 저장한다

- 레포에 `docs/`가 있으면 → `docs/specs/<slug>.md`
- 없으면 → `specs/<slug>.md`
- 사용자가 경로를 지정하면 그것을 우선한다

명세가 여럿이고 하나의 대상(플랫폼, 서비스, 화면)에 묶이면 그 이름의 폴더를 만들고 **파일 이름에서 그 이름을 뺀다.** `specs/programmers/accepted-detection.md`이지 `specs/programmers-accepted-detection.md`가 아니다. 폴더가 이미 말하는 것을 파일 이름이 다시 말하면 목록이 접두사로 뒤덮여 무엇이 다른지 읽기 어려워진다. 폴더를 만들면 명세끼리의 상호 링크는 형제 경로가 되고 색인의 링크는 폴더를 앞에 붙인 경로가 되므로, 옮긴 뒤 링크 검사를 다시 돌린다.

`slug`는 kebab-case 기능 이름이다. 산출물 언어는 한국어가 기본이고, 사용자가 영어를 요청하면 영어로 쓴다(린터의 한국어 어미 검사는 영어 명세에서 경고로만 뜬다).

## 절대 규칙

- 클래스·메서드·타입·변수·파일 이름을 명세 본문에 쓰지 않는다. 코드 블록을 넣지 않는다.
- 관측되지 않는 것은 쓰지 않는다. 내부 캐시, 리팩터링 흔적, 성능 최적화는 사용자가 체감하는 결과로 환산되지 않으면 삭제한다.
- 코드에 없는 동작을 명세에 넣지 않는다. "아마 이렇게 하려던 것"은 `열린 질문`으로 간다.
- Acceptance는 사람이 그대로 손으로 따라 할 수 있어야 한다. 코드를 열어야 확인 가능한 항목은 Acceptance가 아니다.
- 현재 동작이 명백히 버그로 보여도 명세에는 **관측된 대로** 적고, 의심은 `열린 질문`에 따로 적는다. 명세를 쓰면서 조용히 고치지 않는다.
