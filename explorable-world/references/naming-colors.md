# 이름 색 규칙 (content.js 의 names)

글을 읽다가 가장 많이 막히는 지점은 **"이 이름은 외워야 하나, 아무거나 써도 되나"** 이다. 엔진이 글자 색으로 답한다.

| 색 | 종류 | 예 | 마우스를 올리면 |
|---|---|---|---|
| 파랑 | 공식 용어 · 함께 쓰는 프로젝트의 정식 이름 | `kubelet`, `replicas`, `Pending`, `containerd` | 그대로 써야 하는 이름 |
| 노랑 | 직접 지은 이름 · 사용자가 정한 값 | `my-shop`, `worker-1`, `nginx:1.27` | 바꿔도 되는 이름 (+ 무엇을 정한 건지) |
| 회색 기울임 | 자동 생성 · 시스템이 붙인 값 | `-7d9f6c-4xk2p`, `10.244.2.4` | 왜 붙었고 언제 바뀌는지 |

자막·패널·코드 어디서나 칠한다(태그 안의 글자는 건드리지 않는다). 범례는 엔진이 자막·패널·도움말 세 곳에 둔다.

## 설정

```js
names:{
  examples:{o:"kubelet", c:"my-shop", a:"-7d9f6c-4xk2p"},   // 도움말 범례 예시
  official:["Deployment","replicas","watch", …],            // 공식 용어 (설명 글에 나오는 것까지)
  projects:["containerd","CoreDNS", …],                     // 함께 쓰는 프로젝트 — 파랑, 설명만 다름
  custom:{"my-shop":"c", "worker-1":"cnode", "my-shop.yaml":"cfile"},   // 직접 지은 이름 → 설명 키
  auto:{"48213":"arv"},                                     // 고정된 자동 값 → 설명 키
  patterns:[                                                // 한 단어에 섞인 이름은 쪼개서 칠한다
    {re:"my-shop-[0-9a-f]{6}-[a-z0-9]{5}", parts:function(m){
      return [["c","c","my-shop"], ["a","ars",m.slice(7,14)], ["a","apod",m.slice(14)]]; }},
    {re:"10\\.244\\.\\d+\\.\\d+", parts:function(m){ return [["a","aip",m]]; }}
  ],
  messages:{ cnode:"<b>직접 정한 이름</b> · 노드 이름은 보통 서버의 호스트 이름을 그대로 써요.", … }
}
```

- `parts` 의 각 항목은 `[종류(o|c|a), 설명 키, 글자]`.
- 설명 키 기본값: `o`, `oext`(프로젝트), `c`, `a`. 그 밖의 키는 `messages` 에 문장을 둔다.
- 단어 경계는 영문·숫자·`-`·`.` 기준이다. `Pod` 는 `RunPodSandbox` 안에서 칠해지지 않는다.

## 분류 판단

- **필드 이름은 공식, 값은 대개 직접 지은 것** — `replicas` 는 파랑, `3` 은 칠하지 않는다. `name:` 은 파랑, `my-shop` 은 노랑.
- **파일 이름은 직접 지은 것** — 그리고 "파일 이름은 등록 이름과 무관하다"를 설명에 둔다.
- **설치할 때 사람이 정한 이름**(노드 이름 `worker-1`)은 노랑 — 설명에 "설치할 때 정한 값".
- **학습자가 정하지 않고 외부가 정한 값은 회색** — 서버 공인 IP(클라우드가 배정), 사설 IP(DHCP·배선이 배정), 임시 포트, 시퀀스 번호, DNS id, 세션 값, 해시. 판단 기준은 **"누가 골랐나"**: 사람이 고르면 노랑, 시스템·외부 서비스가 정하면 회색. 설명에 누가 정하는지 적는다("호스팅 업체가 배정 — 주인은 이 값을 DNS 에 적어 둘 뿐"). 같은 지도 안에서 서버 IP 를 어떤 곳은 노랑, 어떤 곳은 회색으로 칠하지 않는다.
- **골라서 적은 외부 이름**(이미지 `nginx:1.27`)은 노랑 — 설명에 "저장소에 있는 이름을 골라 적은 것".
- **자동 생성은 왜 붙는지가 핵심** — 해시는 "설계도로 계산", 무작위 문자는 "겹치지 않게", IP 는 "어느 대역에서 누가 골라 줌".
- **평범한 영어 역할 단어는 `official` 에 넣지 않는다** — `Eavesdropper`, `Router`, `ISP`, `Browser` 는 공식 용어가 아니라 그냥 그 역할을 부르는 말이다. 파랑으로 칠하면 "그대로 써야 하는 이름"으로 오해한다. 프로토콜·헤더·필드·도구의 정식 이름(`ClientHello`, `Strict-Transport-Security`, `curl`)만 넣는다. `utf-8` 처럼 코드에 나오는 값 이름도 칠할 거면 규칙에 넣는다(`check_world.mjs` 경고).
- **짧은 숫자·한 글자 공식 용어는 `official` 에 넣지 않는다** — `80|443|53` 을 파랑으로 두면 `(53)` 같은 무관한 숫자도, `A`·`IN` 은 글 속 낱글자도 칠해진다. 필요하면 `patterns` 로 문맥을 잡는다.
- 공식 용어를 너무 많이 넣으면 글이 온통 파랑이 된다. **본문에 실제로 나오는 것만** 넣는다.

## 예시 이름

- 공식 키워드처럼 보이는 이름(`web`, `app`, `test`, `server`)은 쓰지 않는다. `my-shop`, `order-api` 처럼 지은 티가 나게.
- **공식 이름이 없는 역할에 하이픈 식별자를 지어내지 않는다** — `real` 칩과 설명에는 `TLS-termination`, `On-path-observer` 대신 "TLS termination (nginx ssl)", "on-path observer" 같은 평범한 말. 하이픈·소문자로 붙인 이름은 보는 사람이 공식 식별자로 읽는다.
- 출력 예시(`kubectl get pod` 의 NAME 열)에 나오는 이름도 `names` 규칙에 걸려야 한다 — `my-shop` 만 노랑이고 `web-7d9f6c-4xk2p` 는 색이 없는 식이면 안 된다. `check_world.mjs` 가 규칙에 안 걸리는 이름 토큰을 경고한다.
- 같은 예시 이름을 사건 전체에서 일관되게 쓴다 — 파일, 리소스, 라벨, 컨테이너 이름, 출력까지.
