# blog-review

블로그 글 하나를 **대화형으로** 리뷰해 학습 노트로 남긴다.

목적은 글 요약이 아니라 **사용자의 사고를 끌어내고 교정하는 것**이다. 직접 겪기 힘든 엔지니어링 상황을 대리 경험하고, 비슷한 문제가 닥쳤을 때 빠르게 접근할 수 있는 **사고 자산**으로 만드는 게 목표다.

## 시작할 때 — 프로젝트 규칙이 먼저다

**프로젝트에 `AGENT.md` / `AGENTS.md` / `CLAUDE.md`가 있으면 먼저 읽는다. 충돌하면 프로젝트가 이긴다.**

이 스킬은 **방법**만 담는다. 아래는 **사람마다 값이 다르므로 스킬이 정하지 않는다** — 프로젝트에서 읽고, 없으면 처음 한 번 사용자에게 묻고 그 답을 프로젝트에 적어둔다.

| 프로젝트가 정하는 것 | 이 스킬의 기본값 |
|---|---|
| 저장 경로 | `reviews/` · `raw/` · `concepts/` (레이아웃 계약은 아래 참고) |
| **태그 어휘** | 없음 — 프로젝트 목록에서 고른다 |
| 진행 주기 · 소요 시간 목표 | 없음 |
| 노트 깊이 기준 | 없음 — 보통 "이 노트만큼"이라고 기준 노트를 하나 정해둔다 |
| 커밋 · 푸시 방식 | 없음 |
| 안 닫힌 질문 · 실습거리 파일 이름 | `QUESTIONS.md` · `TRY.md` |

> **레이아웃 계약:** `scripts/write_raw.py`가 `reviews/<id>.md` 와 `raw/<id>.jsonl` 이 **형제 디렉터리**임을 검증한다. 이 두 경로만은 프로젝트가 바꿀 수 없다.

## 3원칙

1. **가볍게.** 습관이 1순위. 못 채운 칸이 있어도 넘어간다. 완벽함보다 연속성. *(구체적 시간 목표는 프로젝트가 정한다.)*
2. **요약을 대신 해주지 말 것.** 문제·해결 정리는 짧게. 사용자가 "내가 이해한 것 / 생각 / 질문"을 내놓게 하고, 거기에 반응한다.
3. **교정을 남긴다.** 확인된 것보다 교정당한 것이 오래 남는다. 노트의 중심은 "내가 이렇게 알았는데 → 진짜는 이거".

## 5단계 흐름

### 1. 링크 접수
사용자가 URL만 준다. 인자로 안 주면 요청한다.

### 2. 뼈대만 깐다
글을 가져와 **메타데이터 + 중립 요약 + 글의 뼈대**만 제시한다.

- 중심 주장 **1개**, 이 접근의 이득, 미해결/한계
- **여기서 평가·의견·교훈을 넣지 않는다.** 내 해석을 먼저 깔면 사용자는 그걸 따라 읽고, 그 순간 이 리뷰는 실패한다.
- 필요하면 두 번째 조회로 기술적 구조를 더 파되, 그것도 사실만.

### 3. 사용자가 날것을 던진다 ← 제일 값진 단계
"이해한 흐름 / 반응 / **모르겠는 것·질문**"을 요청하고 **기다린다.**

막히면 질문 1개만 나와도 성공이다. 사용자가 아무것도 안 냈는데 4단계로 넘어가지 않는다.

### 4. 교정 대화
각 항목에 표기해 답한다.

| 표기 | 쓸 때 |
|---|---|
| `✅ 맞음` | 정확함. 왜 맞는지 한 줄 덧붙이면 더 남는다 |
| `🔧 교정` | 틀렸거나 절반만 맞음. **무엇을 무엇으로** 바꾸는지 명확히 |
| `💡 한 단계 더` | 맞지만 더 갈 수 있음. 전이 가능한 형태로 |

- **정확성 최우선.** 틀린 걸 확인해주지 않는다. "절반만 맞음"이면 그렇게 말한다.
- 꼬리 질문 환영. 사용자가 더 파면 계속 간다.
- 사용자가 이해도 확인을 원하면 문제를 내고 채점한다.

### 5. 노트로 묶고 저장한다
이 단계에서만 파일을 쓴다. **대화 중에는 아무것도 저장하지 않는다.**

1. 노트를 `reviews/YYYY-MM-DD-회사-키워드.md`로 저장 (`references/note-format.md` 형식)
2. **범용 개념은 `concepts/`로 분리** — 노트엔 링크만
3. raw 입력을 JSONL로 저장 (`references/raw-capture.md`)
4. 해당되면 `QUESTIONS.md` / `TRY.md` 갱신
5. `README.md` 등 색인 갱신
6. 프로젝트 커밋 규칙이 있으면 따른다

## 개념은 노트에 쓰지 않는다 — 개념 사전으로 뺀다

범용 용어·기술 개념(웹뷰가 뭔가, 번들러가 뭔가)은 **글이 없어도 재사용되고 다음 글에서 또 나온다.** 노트에 흩어놓으면 인출이 안 되고 설명이 중복된다.

- **가르는 선:** *그 글의 논지를 이루는가?* → 노트에 남긴다. *글이 없어도 성립하는 정의인가?* → `concepts/`로 뺀다.
- 노트에는 **링크만** 걸고, **"이 글에서 그게 왜 중요한가"** 한 줄을 남긴다. 개념 설명을 노트에 다시 적지 않는다.
- 개념 하나 = 파일 하나. 파일명은 영문 케밥 슬러그, 제목은 한글/원어.
- 각 개념 파일 끝에 관련 개념 링크와 처음 나온 노트 링크. `concepts/README.md` 목록에도 한 줄.
- 같은 개념이 다시 나오면 **새로 설명하지 말고 그 파일을 갱신**한다.

## 노트끼리 링크한다

이전 노트와 **같은 모양의 패턴**이 나오면 그 자리에서 링크한다.

> `([이전 노트 제목](2026-03-02-acme-....md)의 "트리거를 밖에서 빌려라"와 같은 모양)`

**패턴 이름으로 링크한다** — 노트 제목만 걸면 왜 연결했는지가 안 남는다.

정기 회고 이벤트 없이도 연결이 상시 쌓이게 하는 장치다.

## 항목이 늘면 자르지 말고 병합한다

`🔁 패턴`이나 교정 항목이 많아져도 **개수 상한을 두지 않는다.** 대화가 좋아서 늘어난 걸 개수로 자르면 내용이 날아간다.

대신 노트를 닫기 전에 훑고 **같은 얘기의 다른 각도인 항목을 하나로 합친다.** 하위 불릿으로 각도를 남기면 내용은 안 잃고 인출 단위만 준다.

- **병합 기준:** *"이 둘이 무너지는 조건이 같은가?"* 같으면 한 항목.

## 중앙 파일 두 개 — 사용자가 남긴 것만

기본 이름은 `QUESTIONS.md`(그날 못 닫은 질문)와 `TRY.md`(직접 해볼 실습 아이디어)다. 프로젝트가 다른 이름을 쓰면 그걸 따른다.

- ⚠️ **에이전트가 멋대로 채우지 않는다.** "해볼 만하겠다" 싶은 건 그 순간 `💡`로만 던지고, **사용자가 넣겠다고 한 것만** 기록한다.
- 질문은 대개 대화로 해소되니 보통 비어 있다. **안 닫힌 것만** 남긴다.
- 항목마다 출처 노트 링크 필수.
- (`concepts/`는 예외 — 대화에서 실제로 설명한 개념은 에이전트가 정리해 넣는다.)

## 시간이 없으면 3단계까지만

링크 + 생각 한 줄 + 질문 한 개만 남겨도 그날은 성공이다. **빈 노트보다 짧은 노트가 낫고, 짧은 노트보다 끊긴 습관이 나쁘다.**

## 참고

- `references/note-format.md` — 노트 형식, 필수/옵션 섹션, 태그 어휘
- `references/raw-capture.md` — 교정 전 사용자 입력 원문 보존 규칙
- `scripts/write_raw.py` — raw manifest 검증 + JSONL 생성 (의존성 없음)

## 끝낼 때 확인

- 저장 경로가 맞는지, 색인이 갱신됐는지, 태그가 어휘와 일치하는지
- 새 개념 파일을 만들었으면 `concepts/README.md` 목록에도 넣었는지
- raw JSONL이 생성됐고 노트 frontmatter의 `raw` 경로와 일치하는지
- 프로젝트 커밋 규칙이 있으면 커밋됐는지
